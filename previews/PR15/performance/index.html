Performance

Marmousi2

The elastic Marmousi2 model (Martin et al., 2006) is the classic benchmark of seismic wave propagation codes (movie and figures: Examples).

Benchmark (examples/benchmark_marmousi2.jl): 2D P-SV on a 5 m grid (3401 × 703 cells), 2 s (5317 steps), PML, an explosion 10 m below the sea surface and 641 receivers; time loop only, the best of two or three runs, on the Apple M4 Max laptop. The other codes ran the same grid, time step and receivers: SeismicWaves.jl (v0.9.1, elastic, threaded CPU backend) and JUDI.jl (v4.1.7 with Devito 4.8.23, elastic, OpenMP, see below).

Marmousi2 has no attenuation: SeismicWavePC.jl then leaves out the memory variables of the attenuation, OpenSWPC updates them. In SeismicWaves.jl most of the time goes to recording the 641 receivers; with a single receiver it reaches 439 million updates per second.

With 12 threads SeismicWavePC.jl and JUDI.jl are equally fast here; on a single thread JUDI.jl is 20% faster. JUDI.jl generates its kernels with Devito: optimized C with OpenMP, which computes the material factors (the harmonic mean of μ for the shear stresses, the damping) once before the time loop, uses the 4th-order stencil everywhere and a simple sponge (SeismicWavePC.jl: the PML, 2nd-order differences next to free surfaces as OpenSWPC, and the harmonic means in every step). On macOS its Julia interface crashed with OpenMP threads, so JUDI's propagators (its Python package pysource) ran directly from Python, with Homebrew's LLVM and OpenMP. JUDI's elastic modelling is forward only (explosions, pressure receivers): its gradients are acoustic. In accuracy both codes converge to the same seismograms; on a model with a flat sea floor SeismicWavePC.jl converges faster with the grid spacing (see Validation).

SeismicWavePC.jl and SeismicWaves.jl save the wavefield every √nt steps or so and recompute the steps in between; JUDI.jl uses optimal checkpointing (Revolve) and has no elastic gradients (its row is the acoustic gradient, a much cheaper equation). The forward times here include the setup.

Seconds per simulation for the two examples, on an Apple M4 Max laptop (12 performance cores, 40-core GPU). These are wall-clock times of a whole run, including setup (and, for OpenSWPC, writing and reading its input files), without snapshots, with the same absorbing boundary in both codes. Each time is the better of two runs, with OpenSWPC and Julia runs alternating. The first run in a new Julia session takes 4–10 s more for compilation.

  • On a single computer, Julia threads are faster than MPI with either code. MPI is meant for several GPUs or computers; with the same number of MPI ranks, OpenSWPC is somewhat faster with the PML.
  • Julia's MPI runs pay a fixed ~0.2–0.5 s for setting up and closing the ImplicitGlobalGrid domain decomposition.

Time loop only, with the Cerjan absorber, in million cell updates per second (higher is better), on an Apple M4 Max laptop (12 performance cores, 40-core GPU). The model is a half-space with Q and a free surface. Both codes ran through their normal drivers; the times have setup subtracted and are the minimum of three runs. You can reproduce them with examples/benchmark.jl.

  • The Julia code is faster than the Fortran code: 1.2–1.7× on one core, and 1.5–1.9× with all cores.
  • On the CPU it runs native Julia loops (Threads.@threads with @simd, vectorized by LLVM), which are 1.5–1.8× faster than the same kernels run through KernelAbstractions' CPU backend. GPUs use KernelAbstractions.
  • 3D runs on CPUs are limited by memory access from about 8 threads on.
  • The Apple GPU is 20–45× faster than one CPU core. NVIDIA (A100) numbers will be added.

The laptop was also busy with other work, so single runs varied a lot; take the numbers as indicative.
